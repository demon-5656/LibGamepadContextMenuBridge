# Проект платформы и публичного API

**Статус: проект требований, не действующая документация API 1.5.2.**

Все новые методы и структуры ниже **предлагаются к реализации**. Вызывать их в текущем релизе нельзя. База анализа: commit `9c5fee6e7ee2677c062b580e78b54546bee7247a`, 11 ноября 2026 года.

Навигация: [Стратегия](PRODUCT_STRATEGY.md) · [Приёмка](ACCEPTANCE_AND_RELEASE.md) · [Текущие контракты](API_CONTRACTS_101051.md).

## 1. Граница задачи

Цель — превратить текущий compatibility bridge в небольшую инфраструктуру gamepad-действий, **не ломая существующий LibCustomMenu-путь**.

Первый новый контракт обслуживает синхронные предметные действия там, где можно надёжно определить выбранный bag/slot. Торговые лоты, результат крафта, mail и другие источники не объявляются автоматически поддерживаемыми для выполнения действий. Информационный tooltip и доступность модифицирующей операции — разные возможности.

### Уже существует

- `LibGamepadContextMenuBridge:RegisterContextMenu(func, category, ...)` и `SetEnabled(enabled)`: [реализация](../LibGamepadContextMenuBridge/LibGamepadContextMenuBridge.lua).
- Перехват подходящих регистраций LibCustomMenu и преобразование поддерживаемых записей.
- Плоское gamepad-представление детей submenu.
- Диагностические методы и настройки.

### Ещё требуется

- Публичная версия контракта, явные capabilities и список поддержанных контекстов.
- Реестр именованных providers с удалением регистрации.
- Нормализованный контекст предмета и защита исполнения при его устаревании.
- Общая модель action/toggle/submenu и определённое поведение при ошибках.
- Рабочий пример внешнего аддона и проверка реальной интеграции.

## 2. Разделение ответственности

Это логические модули. Перечень **не означает**, что уже созданы соответствующие файлы или нужны отдельные ZIP.

| Слой | Отвечает за | Не должен делать |
|---|---|---|
| Core | Реестр providers, контекст, валидация, сборка и активация действий | Зависеть от TTC или реализовывать бизнес-логику стороннего аддона |
| Legacy adapter | Преобразование поддерживаемых LibCustomMenu entries | Повторять callback после ошибки, держать глобальный capture открытым через таймеры |
| Gamepad adapter | Представление, навигация, фокус, отображение disabled/checked | Решать, можно ли продать или удалить предмет вместо владельца действия |
| Optional info | Цены, vendor/junk metadata, crafting estimates | Ломать core при недоступных данных |
| Settings / diagnostics | Доступные настройки и объяснение статуса | Публиковать личные данные и включать verbose по умолчанию |

Для первой реализации сохранить текущую обязательную зависимость `LibCustomMenu>=730`. Возможное снятие зависимости с core — отдельное решение после проверки загрузки и миграции, не побочный эффект рефакторинга.

## 3. Предлагаемый API v1

**Имена предварительные; ни один из методов этой таблицы пока не обещан текущим релизом.** Номер контракта независим от версии addon и существующего `minor=152`.

| Предлагаемый метод | Вход | Результат / правило |
|---|---|---|
| `GetAPIVersion()` | Нет | Целое число версии нового контракта; первый реализованный контракт — `1` |
| `GetCapabilities()` | Нет | Снимок поддержанных source/type; недоступная возможность не маскируется под поддержку |
| `RegisterActionProvider(providerId, definition)` | Непустой namespaced ID, определение provider | `handle` при успехе либо `nil, errorCode`; некорректная регистрация не меняет реестр |
| `UnregisterActionProvider(handle)` | Handle полученной регистрации | `true`, если удалена; `false`, если уже удалена или неизвестна. Повторное удаление безопасно |

### Определение provider

- `apiVersion = 1` — явное согласие с контрактом.
- `displayName` — человекочитаемое имя источника действия.
- `sources` — подмножество capabilities библиотеки, без wildcard «везде».
- `priority` — необязательный целочисленный порядок; одинаковый priority упорядочивается по стабильному provider ID.
- `build(context)` — синхронно возвращает список описаний действий. Ничего не продаёт, не удаляет и не меняет в игре.

Идентификатор вида `MyAddon:inventory` относится к namespace владельца. Повторная регистрация того же ID возвращает явную ошибку `DUPLICATE_PROVIDER`; скрытого накопления или неявной замены нет. Для замены владелец сначала удаляет свой handle. Handle должен отличать старую регистрацию от новой: старый handle не удаляет повторно зарегистрированного provider.

Неизвестная major-версия возвращает `UNSUPPORTED_API`. Дополнительные необязательные поля в пределах v1 допускаются только по документированным правилам; неизвестные типы действий не выполняются.

Пилотный справочник ошибок: `INVALID_PROVIDER`, `DUPLICATE_PROVIDER`, `UNSUPPORTED_API`, `UNSUPPORTED_SOURCE`. Это проект семантики; окончательный набор фиксируется вместе с реализацией и тестами.

## 4. Предлагаемый контекст предмета

Контекст — снимок текущего выбора, **не разрешение выполнить действие позже без повторной проверки**.

| Поле | Назначение / правило |
|---|---|
| `source` | Документированный источник; начальный набор определяется capabilities и реальной проверкой inventory/bank, а не названием UI-класса |
| `itemLink` | Полная ссылка на вариант предмета; не уникальный идентификатор физического экземпляра |
| `bagId`, `slotIndex` | Текущая позиция для bag-backed источников; не смешивать с индексом торгового лота |
| `stackCount` | Наблюдаемое количество в момент построения |
| `itemUniqueId` | Идентификатор экземпляра, если доступен и корректно получен; иначе `nil`, а не выдуманное значение |
| `isBound`, `isJunk` | Доступные состояния; неизвестно — `nil`, не автоматически `false` |
| `generation` | Токен текущего выбора/обновления; устаревший результат не применяется к новому выбору |

Не выдавать живой UI-control за стабильный контракт. Legacy adapter может работать со старым control внутри, но новый provider получает только документированные данные. Внутренние таблицы и private-поля bridge не являются частью API.

Provider считает контекст read-only. В Lua это не гарантируется обычной таблицей: core должен изолировать снимки или передавать копии так, чтобы один provider не портил данные другого. Способ изоляции выбирается после замера стоимости; нельзя обещать её без реализации.

### Проверка перед выполнением

1. Убедиться, что мост включён, provider зарегистрирован, сцена и выбранный source ещё актуальны.
2. Получить свежий контекст и сопоставить generation и идентичность предмета. Сравнения одного `itemLink` недостаточно.
3. Если предмет перемещён, стек изменился или соответствие экземпляра доказать нельзя — отменить старую активацию и обновить меню. Не выполнять действие над «похожим» предметом.
4. Повторно проверить `enabled` и прочие условия действия.
5. Передать свежий контекст в callback ровно для этой пользовательской активации. Не делать автоматический retry.

Гарантия здесь — **не более одного вызова callback на принятую активацию**, а не транзакционное exactly-once выполнение игровой операции. Callback может частично изменить состояние и затем бросить ошибку; библиотека не может автоматически отменить это.

## 5. Предлагаемая модель действия

| Поле | Обязательность | Контракт |
|---|---|---|
| `id` | Да | Стабильный ID внутри provider; глобальный ключ — provider ID + action ID |
| `type` | Да | `action`, `toggle` или `submenu` |
| `label` | Да | Непустой отображаемый текст; не идентификатор |
| `enabled` | Нет | Boolean или чистая функция от context; по умолчанию `true` |
| `disabledReason` | Нет | Текстовая причина недоступности, если есть что объяснить игроку |
| `tooltip` | Нет | Дополнительная короткая подсказка |
| `execute` | Для `action` / `toggle` | Callback с контрактом ниже; для submenu-parent необязательное самостоятельное действие |
| `checked` | Для `toggle` | Boolean или чистая функция от context; источник истины — provider |
| `children` | Для `submenu` | Список дочерних описаний; начальный контракт — один уровень, без произвольной рекурсии |

### Семантика исполнения

- Новый `action`: `execute(context)`.
- Новый `toggle`: `execute(context, newState)`, после вызова состояние перечитывается у provider. При ошибке UI не заявляет, что переключение успешно.
- `submenu` не исполняет parent callback при открытии или выборе ребёнка. Самостоятельное действие родителя показывается отдельно.
- `enabled=false` не вызывает `execute`. Если выбранный renderer не поддерживает понятное disabled-представление, запись скрывается; поведение capability должно быть явно описано.
- Невалидная запись пропускается с диагностикой. Остальные корректные действия других providers остаются доступны.

Эти новые сигнатуры **не применяются к legacy callbacks**. Поддерживаемый legacy label action вызывается без аргументов, submenu-checkbox child — с новым boolean-состоянием. Genuine mouse parent callback требует реальный control, top-level checkbox — control и state; в текущем review-fix эти формы и control-dependent submenu evaluators/builders не эмулируются и пропускаются с диагностикой. Наличие parent execution в предлагаемом API не обещает его поддержку старым adapter.

### Идентичность и дубли

В новом API совпадение названий двух разных действий не делает их одним действием: дедупликация по ID, не по тексту. При неоднозначности UI показывает источник. Дубли одного action ID внутри ответа provider считаются ошибкой ответа с детерминированным результатом и диагностикой.

Существующий legacy-путь [сравнивает имена](../LibGamepadContextMenuBridge/LibGamepadContextMenuBridge.lua). Не обещать устранение всех коллизий старых меню без изменения и отдельной проверки adapter. Автоматически сопоставлять legacy-действие и новое действие по похожему label нельзя; стратегия миграции provider должна исключить двойную регистрацию.

## 6. Жизненный цикл и ошибки

Последовательность: текущий выбор → снимок context → подходящие providers → проверка описаний → построение UI → пользовательская активация → свежая проверка → callback → обновление по актуальному состоянию.

- При закрытии меню, смене сцены или выбора инвалидировать generation и ожидающие обновления.
- После unregister не показывать и не исполнять действия старого provider; закрыть либо перестроить открытое меню.
- `build` и вычисляемые поля не должны иметь побочных эффектов; core не может исправить нарушающий этот контракт сторонний код.
- Ошибка provider перехватывается и помечается его ID. Здоровые providers не вызываются повторно для компенсации чужой ошибки.
- `pcall` не умеет прервать зависший синхронный callback. Не обещать sandbox, защиту от зависания или полную изоляцию недоверенного кода.
- Начальный API синхронный. Async builders, ожидание HTTP и глобальный capture через таймеры не поддерживаются. Будущее async-расширение потребует отдельного протокола отмены и versioned capabilities.
- Порядок детерминированный: provider priority/ID, затем порядок записей в его ответе.

## 7. Миграция без поломки текущих пользователей

1. Сохранить текущий `RegisterContextMenu` и legacy callback contract; не переименовывать SavedVariables и install folder.
2. Ввести новый provider registry параллельно, за отдельным внутренним путём. Все методы выше сначала реализовать и протестировать, только потом показывать как available API.
3. Описать precedence между native, legacy и новым provider-путями. Не удалять уже работающие native actions ради новой оболочки.
4. Первый addon-example использует только новый API, проверяет его наличие и версию. На 1.5.2 не пытается вызвать отсутствующий метод и не ломает остальной аддон.
5. Для переноса реального аддона выбрать один путь регистрации действий: новый либо legacy. Не включать оба молча.
6. Не менять schema SavedVariables без реального изменения схемы. Если оно необходимо — отдельная миграция с сохранением пользовательских настроек и проверкой отката.
7. Стабильный v1 публикуется после пилота; несовместимое изменение требует нового major-контракта и переходного периода. Новая версия addon не автоматически новая версия API.

Первая архитектурная итерация не требует массового переписывания большого Lua-файла. Выделять один слой за раз, сохраняя проверяемое поведение.

## 8. Пакет разработчика

До приглашения внешних авторов подготовить:

- Работающий `example addon` с manifest, минимальным действием и toggle; это будущий артефакт, сейчас его нет.
- Краткое руководство: dependency/load order, проверка API version, регистрация, teardown, диагностика.
- Reference таблиц provider/context/action и список error codes.
- Пример отказа для неподходящего предмета и stale context.
- Публичный changelog контракта и правила deprecated API.
- Реальную матрицу проверенных ESO/LibCustomMenu/UI-комбинаций.

Не публиковать псевдопример с новыми вызовами как готовый copy/paste-код до реализации. Текущие ограничения adapter описаны в [API contracts](API_CONTRACTS_101051.md); [addon README](../LibGamepadContextMenuBridge/README.md) предназначен игрокам.

## 9. Приёмка первого нового контракта

- [ ] Регистрация, отказ при дублировании, unregister и старый handle проверены на реально загруженной библиотеке.
- [ ] Provider error не лишает пользователя здорового действия другого provider.
- [ ] Action, toggle, submenu-parent и child выполняют документированные сигнатуры.
- [ ] Одно нажатие не вызывает callback повторно после исключения.
- [ ] Смена предмета, количества, сцены и unregister блокируют устаревшую активацию.
- [ ] Разные IDs с одинаковым label не теряют действия.
- [ ] Legacy callbacks не получают новые context-аргументы.
- [ ] Без TTC и без LibAddonMenu базовый actions-путь не зависит от этих интеграций.
- [ ] Документированный пример прошёл запуск в ESO, а не только Lua-заглушки.
- [ ] Целевые затраты на построение/обновление измерены в одинаковом сценарии с baseline; допустимый бюджет выбран по измерениям, а не выдуман.

Ни один пункт не считается выполненным наличием этого документа. Общая игровая приёмка — в [ACCEPTANCE_AND_RELEASE](ACCEPTANCE_AND_RELEASE.md).
