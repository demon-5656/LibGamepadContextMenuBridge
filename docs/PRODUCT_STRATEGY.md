# От «просто мод» к «мне это точно нужно»

**Статус: план развития, не описание уже выпущенной платформы.**

База: LibGamepadContextMenuBridge 1.5.2, commit `9c5fee6e7ee2677c062b580e78b54546bee7247a`. Документ подготовлен 11 ноября 2026 года.

Навигация: [README](../README.md) · [Проект платформы и API](PLATFORM_SPEC.md) · [Приёмка и выпуск](ACCEPTANCE_AND_RELEASE.md).

## 1. Какой продукт мы строим

**Обещание игроку:** «Полезные действия твоих аддонов доступны с геймпада — без постоянного переключения на мышь».

**Обещание разработчику:** «Опиши действие и условия его доступности. Библиотека отвечает за gamepad-представление, контекст и жизненный цикл».

Это два разных пути к одной цели:

- Игрок устанавливает мост, потому что возвращается конкретное нужное действие.
- Автор аддона использует библиотеку, потому что ему не приходится поддерживать собственные gamepad-хуки.

Нельзя сделать аддон необходимым буквально каждому игроку. Первая аудитория — **игроки ESO на ПК с геймпадом, использующие аддоны с подходящими предметными действиями**. Поддержка консолей, всех интерфейсных модов и любых клавиатурных меню здесь не обещается.

## 3. Что должно вызвать «мне это нужно»

### Сценарий A. Нужное действие больше не требует мыши

Игрок открывает предмет, находит привычную команду своего аддона и выполняет её с геймпада. Ему не нужно знать, что такое registry, hook или callback.

**Демонстрация:** один предмет, один реальный сторонний аддон, одинаковая операция до установки и после. Показать не только появление строки, но и фактический результат действия.

**Условие успеха:** действие выполняется по выбранному предмету, без дублей и без поломки исходного клавиатурного пути.

### Сценарий B. Решение по предмету видно рядом с ним

Игрок видит нужную информацию, не открывая дополнительные окна: доступную цену, статус предмета, оценку материалов там, где она уместна.

**Условие успеха:** информация читается в игровой конфигурации пользователя, не перекрывает интерфейс, не остаётся от прошлого предмета. Нет данных — интерфейс честно показывает ограничение.

Это усиливает ежедневную пользу, но **не является главным основанием платформы**. Ценовой блок не должен становиться обязательным для автора, которому нужны только действия.

### Сценарий C. Другой автор не пишет свой gamepad-слой

Автор подключает документированный интерфейс, регистрирует действие, проверяет его на двух предметах и получает работающий gamepad-путь.

**Условие успеха:** интеграция использует публичный контракт, не требует private `_...` методов и воспроизводится вне авторского тестового стенда.

## 4. Что важно разным пользователям

| Аудитория | Боль / гипотеза | Приоритетный результат | Чего не обещаем |
|---|---|---|---|
| Игрок с предметными аддонами | Нужная команда исчезает при игре с контроллером | Проверенные конкретные действия без смены ввода | Автоматическое исправление любого аддона |
| Игрок, работающий с торговлей и крафтом | Для решения не хватает контекстной информации | Компактные достоверные подсказки | Автоторговлю и гарантированный заработок |
| Автор аддона | Повторяет gamepad-интеграцию и чинит её после изменений UI | Небольшой стабильный API и рабочий пример | Полное освобождение от тестирования своего callback |
| Игрок с крупной UI-модификацией | Дубли, конфликтующие меню, непонятно, кто добавил действие | Проверенная комбинация и понятная диагностика | Совместимость со всеми сборками без проверки |

Это продуктовые гипотезы. Интервью, результаты пользовательских сессий и подтверждённые интеграции ещё нужно собрать. Исследование текущих аналогов в рамках подготовки этих документов не проводилось; заявлений «единственный на рынке» нет.

## 5. Порядок развития

Номера этапов — порядок принятия решений, не обещанные даты или номера будущих релизов.

| Этап | Что делаем | Что получает пользователь | Условие перехода дальше |
|---|---|---|---|
| A. Доверие к основе | Проверить 1.5.2 в игре, сохранить короткую матрицу совместимости, закрыть воспроизведённые блокеры | «Я могу оставить это включённым» | Пройдены применимые обязательные сценарии из документа приёмки; нет открытых блокеров целевого пути |
| B. Понятная ежедневная польза | Короткое описание, инструкция, демонстрация до/после, минимальные дефолты, объяснимые состояния без данных | «Я понял пользу сразу после установки» | Независимые тестеры находят и выполняют целевое действие без помощи автора |
| C. Интерфейс для разработчика | Реализовать малый provider API v1, контекст и lifecycle; сохранить legacy-мост | «Моему аддону проще добавить поддержку» | Публичный пример работает в игре; контракт проверен на ошибках, отключении и смене предмета |
| D. Реальные внешние интеграции | Найти авторов, помочь с подключением, документировать точные версии | «Мои любимые аддоны уже используют это» | Два независимых внешних аддона применяют публичный API и прошли совместную проверку |
| E. Расширение по спросу | Добавлять новые контексты и UI только по реальным запросам | Польза растёт без усложнения базовой установки | Для каждого расширения есть пользовательский сценарий, владелец и проверка |

Не ждать завершения всех этапов, чтобы показать полезный мост игрокам. Но не продавать этап C как готовый API, пока он существует только на бумаге.

## 6. Первый рабочий backlog

Каждый пункт — отдельная задача. Реализация не входит в подготовку этой документации.

| ID | Приоритет | Изменение | Зависимость | Критерий готовности |
|---|---|---|---|---|
| P-01 | Первый | Внутриигровая приёмка базовых действий и overlay | Нет | Заполненная матрица с версиями ESO/библиотек и фактическими результатами; конкретные FAIL заведены отдельно |
| P-02 | Первый | Выбрать первый показательный сторонний аддон | P-01 для заявления о поддержке | Есть проверенная операция и разрешённая демонстрация; название не объявлено поддерживаемым заранее |
| P-03 | Первый | Переупаковать страницу продукта и первый запуск | P-02 | Игрок видит пользу, зависимости и ограничения до установки; есть короткое видео или реальные кадры до/после |
| P-04 | Следующий | Логически отделить actions от pricing/crafting/settings | P-01 | Ценовые сбои не ломают действия; старые настройки и сценарии сохранены; без обязательного дробления ZIP |
| P-05 | Следующий | Provider API v1 и явный контекст предмета | P-04 | Выполнены контракты и критерии [PLATFORM_SPEC](PLATFORM_SPEC.md); legacy API сохранён |
| P-06 | Следующий | Публичный пример и инструкция автору | P-05 | Чистая установка примера и основной библиотеки даёт наблюдаемое действие; нет private API |
| P-07 | После пилота | Две внешние интеграции | P-06 | Приняты авторами, проверены на конкретных версиях, есть ссылки и канал обратной связи |
| P-08 | По потребности | Меню-группы, избранное, новые источники | Подтверждённая проблема пилота | Для каждой возможности показано, какой лишний шаг она убирает и что не ломает |

**Первая итерация — P-01 → P-02 → P-03.** Большой новый API не заменяет доказательства, что игроку уже стало удобнее.

## 7. Как не превратить библиотеку в комбайн

- Сохранять `LibGamepadContextMenuBridge` как техническое имя и текущую установочную папку. Человеческий подзаголовок можно сделать понятнее без переименования идентификаторов.
- Сначала разделить ответственность внутри проекта. Отдельные пакеты, репозитории и обязательные зависимости вводить только при реальной необходимости.
- Core отвечает за контекст, сборку действий и gamepad-представление. Цены, crafting и дополнительные панели — необязательные потребители.
- Не переписывать всё ради красивой архитектуры: переносить небольшой участок с проверкой прежнего поведения.
- Не добавлять телеметрию, аккаунт или сетевой сервис ради оценки востребованности. Для пилота достаточно добровольных отчётов и интервью.
- Не делать встроенные автоудаление, массовую продажу или автопокупку способом привлечения аудитории. Мост не должен обходить игровые ограничения и защиту исходного аддона.

## 8. Почему разработчику выгодно подключаться

Нужны четыре вещи: стабильный контракт, быстрый первый результат, понятные ошибки и поддерживаемый пример. Большой список методов сам по себе не создаёт экосистему.

Пакет для первого внешнего автора:

1. Одна страница «что библиотека берёт на себя и чего не делает».
2. Минимальный работающий addon-example с публичным API.
3. Таблица контекстов, типов действий и версий API.
4. Сценарии смены предмета, callback error, отключения и повторной регистрации.
5. Канал для issues и политика совместимости.

Пока автор использует private методы или копирует хуки из исходника, платформа ещё не состоялась.

## 9. Как понять, что переход произошёл

Пороговые значения ниже — **предлагаемые цели пилота**, не измеренные результаты и не требования к каждому patch-релизу.

| Сигнал | Как проверяем | Предлагаемый ориентир |
|---|---|---|
| Быстро понятна польза | Дать установку и один сценарий без устных подсказок; записать время до успешного действия | Первое полезное действие за две минуты после загрузки персонажа, когда зависимости уже установлены |
| Аддон нужен не только автору | Добровольные отчёты после обычной игры | Пять независимых тестеров; у каждого три игровые сессии с нужным действием |
| Уходит переключение ввода | Сравнить один и тот же сценарий с мостом и без него | Целевая операция выполняется только с геймпада; исходное число переключений записано, а не придумано |
| API действительно удобен | Наблюдать первое подключение внешнего автора | Первое действие за пятнадцать минут после подготовки окружения; ожидание установки исключено из времени |
| Возникает экосистема | Ссылки на принятые внешние интеграции и их проверенные версии | Два внешних автора, не два примера внутри этого репозитория |
| Базе доверяют | Реальная приёмка и добровольные сообщения о проблемах | Нет открытых критических дефектов, которые ломают выбранный обязательный сценарий |

Скачивания и favourites полезны для общей картины, но не доказывают активное использование, удержание или совместимость. Если данных недостаточно, результат — «неизвестно», а не «цель достигнута».

## 10. Подача продукта

Черновик первого экрана для игрока:

> Играешь в ESO на ПК с геймпадом, а нужные действия аддонов остаются в меню мыши? LibGamepadContextMenuBridge переносит поддерживаемые предметные действия LibCustomMenu в gamepad-меню. Посмотри проверенные сочетания аддонов и пример до/после.

Черновик обращения к автору **после реализации и приёмки нового API**:

> Добавь действие через публичный provider API. Библиотека займётся gamepad-меню и жизненным циклом контекста; логика самого действия остаётся у твоего аддона.

Это заготовки, не разрешение публиковать недоказанные обещания. До публикации подставить реальные проверенные сочетания, а не названия желаемых интеграций. Не использовать «обязателен всем», «поддерживает любые аддоны», «полностью безопасен» или «гарантирует прибыль».

## 11. Что сознательно откладываем

Полную замену gamepad UI, собственный marketplace, облачный аккаунт, универсальную экономическую платформу, автоматические массовые действия, поддержку всех окон игры, переписывание всех сторонних аддонов. Эти направления не нужны для доказательства первой ценности.

**Проверка любой новой идеи:** она убирает конкретное лишнее действие игрока, снижает работу внешнего автора или устраняет воспроизведённую проблему? Если нет — пока не делать.
